# DickCraftTg

Telegram-игра для групп на Python 3.10+. На Windows дополнительно установите базу часовых поясов: `py -m pip install tzdata`. На Linux обычно используется системная база часовых поясов.

## Запуск

1. Создайте бота в @BotFather. Сохраните токен в защищённой переменной окружения `BOT_TOKEN`, не в Git и не в чате.
2. Укажите `OWNER_ID` — положительный числовой Telegram ID вашего личного аккаунта (не username и не ID группы). Эта настройка обязательна; без неё бот не запустится. Откройте личный чат с ботом и отправьте `/start`, затем `/admin`, для просмотра заявок.
3. В @BotFather выполните `/setprivacy` → выберите бота → Disable. Затем удалите и заново добавьте бота в группу. Это нужно для распознавания кириллических команд: Telegram не считает их стандартными bot commands. Боту не нужны права администратора. После отключения privacy бот получает обычные сообщения; код обрабатывает только команды.
4. Из корня репозитория запустите `python3 bot.py`. Используется long polling; публичный сервер и входящий порт не нужны. Запускайте только один экземпляр на токен. Нужен HTTPS-доступ к `api.telegram.org`.
5. Одобрите группу в личных сообщениях боту. Затем в группе отправьте `/писюн`, повторите команду для проверки дневного ограничения, затем `/мой_писюн`, `/топ`, `/чат`.

Необязательные настройки:

- `DB_PATH`: путь SQLite, по умолчанию `data/game.sqlite3`. Сохраняйте базу между перезапусками; для резервного копирования используйте SQLite backup API или останавливайте бота и копируйте все файлы базы вместе с WAL.
- `GAME_TIMEZONE`: часовой пояс IANA, по умолчанию `Europe/Moscow`.

## Правила

Каждая пара «участник + беседа» начинает с 0 см. `/писюн` один раз за календарный день выбирает рост с вероятностью 70% или уменьшение с вероятностью 30%; величина изменения — от 1 до 10 см. Допускаются отрицательные значения. `/мой_писюн` показывает результат. `/топ` выводит 10 игроков, `/топ_все` — всех игравших в беседе (длинный список разбивается на сообщения). `/чат` суммирует их длины. `/ролл` выдаёт число 1–100 без дневного лимита.

Рейтинг включает только игравших, а не всех участников Telegram-группы. Бот не удаляет результат при выходе участника. Перенос рейтинга при миграции обычной группы в супергруппу пока не реализован. Общего рейтинга между беседами нет: его команда и правила в предоставленном описании отсутствуют.

## Проверки

```sh
python3 -m unittest discover -s tests -v
```

Проверяются дневной лимит и московская полночь, разделение бесед, рейтинг, сумма, сохранение в SQLite, адресация команд, ролл и разбиение сообщений. Для проверки реального обмена с Telegram требуется токен и группа.

## Ввод команд

Команды вводятся вручную. Бот не показывает клавиатуру с кнопками и при каждом ответе скрывает ранее добавленную клавиатуру. После обновления отправьте `/help`, чтобы убрать старые кнопки.

При запуске бот удаляет ранее зарегистрированный общий список команд Telegram. Кириллические команды и латинские варианты `/grow`, `/mine`, `/top`, `/top_all`, `/chat`, `/roll`, `/help` продолжают работать при ручном вводе.


## Панель владельца и одобрение групп

Панель доступна только аккаунту из `OWNER_ID` и только в личном чате с ботом:

- `/admin` — справка по управлению.
- `/pending` — ожидающие одобрения заявки с ID чатов.
- `/chats` — все известные чаты и их статусы (`pending`, `approved`, `denied`).
- `/approve -1001234567890` — разрешить работу в указанном чате.
- `/deny -1001234567890` — запретить работу, в том числе отозвать ранее выданное разрешение.

При добавлении бота в группу сообщение о необходимой верификации появляется в самой беседе. Владелец бота получает личное уведомление о новой заявке с названием беседы, ID и командами решения. Владелец беседы личных уведомлений не получает. Для получения уведомлений владелец бота должен заранее открыть личный чат с ботом и отправить `/start`. Владелец бота просматривает заявки через `/pending` и принимает решение командами `/approve ID` или `/deny ID`. Если событие добавления было пропущено, заявка создаётся при первой поддерживаемой команде. До одобрения игровые команды заблокированы. Администраторы групп не могут одобрять заявки. Telegram позволяет добавить бота без предварительного разрешения владельца: проверка ограничивает его работу уже после добавления. При запрете бот остаётся в группе, но не выполняет игровые команды.

Решения сохраняются в отдельной таблице SQLite и переживают перезапуск и повторное добавление бота. Старые результаты игроков сохраняются. Все существующие группы после обновления также требуют одобрения; миграция в супергруппу создаёт новый ID и требует нового разрешения. Заявки сохраняются независимо от доставки сообщения в беседу и доступны через `/pending`.

Опрос получает `message`, `my_chat_member` и `callback_query`. Ответы доставляются через сохраняемую очередь, описанную ниже.

Дополнительные тесты проверяют запрет игры до одобрения, права владельца, личные уведомления только владельцу бота и отсутствие дубликатов, отзыв разрешения, повторное добавление и сохранение решений после перезапуска. Реальный обмен с Telegram требует настроенных `BOT_TOKEN`, `OWNER_ID` и тестовой группы.


### Повторная заявка после отказа

Владелец или администратор беседы может отправить `/verify` (или `/verify@имя_бота`) в самой беседе. Права проверяются через Telegram `getChatMember`; для гарантированной проверки других участников Telegram требует, чтобы бот был администратором. При ошибке проверки заявка не меняется. Анонимному администратору нужно отправить команду от своего личного аккаунта.

После отказа `/verify` переводит единственную запись беседы из `denied` в `pending`. Пока заявка активна, повторная команда сообщает об ожидании решения и не создаёт дубликат. Для уже одобренной беседы новая заявка не создаётся. Обычные команды и повторное добавление бота не отменяют отказ. Подтверждение повторной заявки появляется в беседе, а владелец бота получает новое личное уведомление. Повторные команды по уже активной заявке не создают новых уведомлений, в том числе после перезапуска. При ошибке личной доставки заявка сохраняется и доступна через `/pending`; ошибка записывается в журнал без токена. Для временных ошибок действует автоматическая повторная доставка через сохраняемую очередь; постоянные ошибки видны в панели.


## Обновление существующего VPS (systemd)

`scripts/update_vps.py` запускается через `sudo python3 scripts/update_vps.py --owner-id ЧИСЛОВОЙ_ID --service ИМЯ.service`. Он поддерживает Linux, где `MainPID` systemd-сервиса — процесс `python ... bot.py`, а рабочая папка — корень Git-репозитория. Docker, supervisor и shell-обёртки не поддерживаются. Если имя сервиса не передано, скрипт запросит его. Требуются `git`, `runuser`, Python 3.10+ и доступ сервера к GitHub.

Скрипт определяет `DB_PATH` из работающего процесса, требует отсутствия локальных изменений отслеживаемых файлов и обновляет код только fast-forward из `origin/main`. После остановки сервиса SQLite backup API создаёт резервную копию в уникальной папке `/var/backups/dickcraft-*`, затем выполняется `integrity_check`. База не заменяется; схема расширяется от имени пользователя сервиса, а все записи игроков сравниваются с копией до запуска. Токен и настройки пути к БД сохраняются. `OWNER_ID` задаётся через systemd drop-in `99-dickcraft-owner.conf`; наличие конфликтующего значения после запуска считается ошибкой. Резервная копия и сведения о предыдущем коммите остаются на сервере.

При ошибке скрипт пытается восстановить предыдущий коммит (в detached HEAD) и свой предыдущий drop-in, затем запустить сервис. Автоматическое восстановление БД из копии не выполняется, чтобы не затереть новые результаты. После успешного обновления проверьте `/admin` в личном чате с ботом и одобрите существующие беседы. Проверка состояния systemd не заменяет проверку ответа бота в Telegram.

## Надёжность и панель владельца

Команды ограничены тремя за 10 секунд на участника в каждой беседе и двадцатью за минуту на беседу. Превышение молча игнорируется; уведомление об ожидании верификации показывается не чаще раза в минуту. Ограничения сохраняются при перезапуске, отдельные беседы не делят лимит. Для команд владельца действуют те же лимиты; кнопки панели их не расходуют.

Ответы и уведомления сохраняются в таблице `delivery` той же SQLite. Изменение результата игры, постановка ответов в очередь и сохранение позиции Telegram выполняются одной транзакцией. Повторное получение уже обработанного обновления не повторяет игру. При временных сетевых ошибках доставка повторяется с увеличивающейся паузой до часа, при Telegram 429 учитывается `retry_after`. Порядок сообщений внутри беседы сохраняется, ошибка одной беседы не блокирует другую. Ошибки 400/401/403/404 считаются постоянными: сообщения остаются со статусом `failed` на семь дней, затем удаляются. Состояние очереди видно в `/admin`; `/retry_delivery` повторно ставит сообщения с постоянными ошибками в очередь. Для личных уведомлений заранее отправьте боту `/start`.

Доставка имеет семантику «как минимум один раз»: если Telegram принял сообщение, а процесс завершился до удаления записи очереди, возможен повтор сообщения. Ожидающие сообщения не удаляются по возрасту. Автоматически сохранённые уведомления, созданные до решения владельца, могут прийти после изменения статуса; кнопка «Открыть заявку» показывает текущее состояние.

`/admin`, `/chats` и `/pending` открывают панель с пятью беседами на странице и кнопками перехода. `/chats 2` и `/pending 2` открывают вторую страницу. `/find ID` показывает карточку беседы, статус и дату заявки; `/history ID` показывает последние 20 решений с временем и ID владельца. История ведётся с этого обновления; для старых заявок без известной даты это явно указано. Решения из карточки проверяют версию заявки, поэтому старые кнопки не изменяют новую заявку. Отключение уже одобренной беседы командой `/deny ID` требует подтверждения кнопкой с названием беседы; подтверждение действует пять минут. Подтверждение можно отменить.

## Ежедневные резервные копии на VPS

После обновления кода выполните от root:

```sh
python3 /opt/dickcraft/app/scripts/install_backup.py --service dickcraft.service
systemctl list-timers dickcraft-backup.timer --no-pager
```

Установщик определяет реальный путь SQLite и пользователя из запущенного сервиса, копирует программу резервного копирования в root-managed `/usr/local/lib/dickcraft/backup_db.py`, устанавливает `dickcraft-backup.service` и `dickcraft-backup.timer`. Сначала выполняется настоящее резервное копирование; расписание включается только при его успехе. Повторная установка обновляет существующие единицы, не создавая дополнительные таймеры.

Копии создаются каждый день около 03:00 по Москве с дополнительной случайной задержкой до 15 минут. `Persistent=true` позволяет выполнить пропущенный запуск после включения VPS. Хранятся 14 последних проверенных снимков в `/var/backups/dickcraft-daily` с доступом только root. SQLite backup API работает без остановки бота и включает данные WAL. Программа выполняет `integrity_check` и публикует готовый снимок атомарно; ротация выполняется только после успешного создания нового. Каталог с готовыми копиями не доступен пользователю бота. Прежние копии перед обновлениями в `/var/backups/dickcraft-*` не затрагиваются.

Проверка вручную и просмотр журнала:

```sh
systemctl start dickcraft-backup.service
journalctl -u dickcraft-backup.service -n 20 --no-pager
```

Это локальные копии на том же VPS: они не защищают от потери диска/сервера. Полное развёртывание systemd проверяется на VPS после установки; локальные тесты проверяют создание снимка живой WAL-базы, восстановление в отдельный файл, целостность и ротацию. Рабочая БД при тестах и резервном копировании не заменяется.
